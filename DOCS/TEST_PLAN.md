# mDNS 网络资产测绘 CLI 工具 —— 边界问题分析与测试计划

## 一、 项目背景与测试目标

本项目旨在开发一个基于 Golang 的高可用、高鲁棒性 mDNS 资产测绘 CLI 工具。在复杂的网络环境与极端输入条件下，程序需保证：
1. **零崩溃（Zero Panic）**：无论接收到何种畸形输入或破损报文，均能防御性拦截并平稳处理。
2. **高保真（High Fidelity）**：解析得到的服务名、IP、端口、深度 TXT Banner 等信息，输出格式必须严格契合测绘规范与题干示例。
3. **可自动化验证（Self-Verifiable）**：不依赖特定物理设备，通过数据驱动的单元测试（Data-driven / Table-driven Unit Tests）实现 100% 覆盖关键边界逻辑。

---

## 二、 核心边界场景、技术风险与解决方案

针对前文梳理的核心流程（输入解析 -> 网络探测 -> 报文解码 -> 深度提取 -> 格式渲染），整理出以下 6 大边界场景：

### 边界 1：参数输入格式异常与越界
* **场景描述**：
  * 用户输入的 IP 不符合规范（如 `999.1.1.1`、包含字母等）。
  * 用户输入的 CIDR 掩码越界（如 `/33`、负数）。
  * 端口格式非法（如端口非数字、范围反写 `80-70`、端口超过 65535 如 `70000`）。
* **潜在风险**：未做参数校验将导致底层系统库抛出异常退出，甚至引发内存暴涨（如误解析出海量非法地址）。
* **解决策略**：
  * 采用强类型输入解析器，利用 `net.ParseIP` 和 `net.ParseCIDR` 进行严格前置校验。
  * 编写端口范围校验器，检查 `min <= max` 且落在 `[1, 65535]` 合法区间内。
  * 捕获并返回语义化友好的命令行帮助与错误提示，退出码为非 0。

### 边界 2：TXT 记录空值、缺失或非标准键值对（深度 Banner 解析防崩）
* **场景描述**：
  * 响应中的 TXT 记录内容为空（0 字节或切片为空）。
  * TXT 记录不含 `=` 分隔符（如纯标签 `just_a_tag`）。
  * TXT 记录包含多个 `=`（如 `path=/?foo=bar` 或 Base64 字符串）。
* **潜在风险**：常规逻辑直接使用 `strings.Split(record, "=")[1]` 提取 value 时，会直接触发 **Index Out of Range（切片下标越界）导致程序 Panic 崩溃**！
* **解决策略**：
  * 使用安全切割方法 `strings.SplitN(record, "=", 2)` 保证至多切分为两部分。
  * 增加切片长度判断，若无等号则作为独立 tag 标签保留，不强制读取 value。
  * 当 TXT 完全为空时，返回空 Banner 字符串，并在输出格式中安全忽略该属性行，不输出空行。

### 边界 3：响应报文缺失 A / AAAA 地址记录（地址回退机制）
* **场景描述**：
  * 目标设备响应了 PTR 和 SRV 记录，但在 Additional Section（附加记录区）中**未附带该主机的 A 记录（IPv4）或 AAAA 记录（IPv6）**。
* **潜在风险**：由于指针解引用（Nil Pointer），程序可能报错或在输出中显示 `IPv4=<nil>`。
* **解决策略**：
  * 建立**地址兜底（Fallback）机制**：如果在 DNS 响应报文中未能提取出主机的 A 记录，则自动取用当前发起探测连接的目标网络 IP 地址作为该服务的 IPv4，保证输出结果的连贯与完整。

### 边界 4：设备多服务聚合与重复报文去重
* **场景描述**：
  * 同一台设备同时暴露多个服务（如威联通 NAS 同时开启 `workstation:9/tcp`、`http:5000/tcp`、`smb:445/tcp` 等）。
  * 由于网络多播/单播的特性，同一服务可能会收到多次响应。
* **潜在风险**：直接按报文流水式打印会导致同一台设备的信息被割裂打散，出现大量重复冗余日志，无法形成题干要求的层次化结构。
* **解决策略**：
  * 在内存中构建以 `(TargetIP, Hostname)` 为联合唯一主键的聚合器对象（`DeviceAsset`）。
  * 采用 `map[string]bool` 对已解析的服务标识和 PTR 记录进行去重过滤；后到达的增量属性（如补充的 TXT Banner）合并入现有设备资产中。

### 边界 5：网络请求静默超时（无响应与防火墙丢包）
* **场景描述**：
  * 探测目标主机处于离线状态，或者存在本地/网络防火墙静默丢弃 UDP 报文。
* **潜在风险**：UDP 是无连接协议，不会收到 RST 或错误包；若缺少超时控制，协程将处于死锁或无限阻塞状态。
* **解决策略**：
  * 针对单次请求设置带缓冲的 Context 超时时间（如默认 2 秒）。
  * 到期若未收到响应，平滑退出并释放 Socket 句柄，继续执行下一个目标探测。

### 边界 6：输出格式与缩进严格一致性
* **场景描述**：
  * 题干要求的输出包括顶层 `services:`、各端口服务详情缩进、冒号语法，以及尾部的 `answers:\nPTR:`。
* **潜在风险**：格式稍有偏差（如大小写不一致、多了空格或换行），可能导致自动化批改测评工具判定结果不匹配。
* **解决策略**：
  * 制定专用的输出渲染器模板，严格对照题目示例构造断言单测，杜绝格式漂移。

## 三、 测试计划与用例设计

测试方案采用纯 Go 标准库 `testing`，完全通过**数据驱动（Table-driven Test）**和**内存模拟（Mock Packet）**的方式运行。

| 用例 ID | 测试模块 | 测试场景 / 输入数据 | 预期结果 |
| :--- | :--- | :--- | :--- |
| **TC-INP-01** | 参数解析 | 输入合法单 IP：`192.168.1.10`，端口：`5353` | 成功解析出 1 个 IP 与 1 个端口，无错误。 |
| **TC-INP-02** | 参数解析 | 输入 CIDR 网段：`192.168.1.0/30` | 成功拆解出 4 个可用 IP 地址，无错误。 |
| **TC-INP-03** | 参数解析 | 输入非法 IP：`256.0.0.1`、非法掩码：`10.0.0.0/33` | 返回格式错误，拦截后续流程。 |
| **TC-INP-04** | 参数解析 | 输入非法端口：`80-70`、`70000`、`abc` | 返回端口区间非法错误，拦截后续流程。 |
| **TC-TXT-01** | Banner 解析 | 标准威联通 TXT：`["model=TS-X64", "fwVer=5.2.9"]` | 正确拼接为 `model=TS-X64,fwVer=5.2.9`。 |

## 四、 自动化测试执行与验收标准

### 1. 执行命令
通过终端执行标准 Go 单测命令：
```bash
go test -v -cover ./...
```

### 2. 验收通过标准
1. **Pass 率**：所有单元测试用例全部 `PASS`，测试成功率为 100%。
2. **零 Panic**：在极端变异数据下未发生任何未捕获的 Panic。
3. **格式完全匹配**：`TC-FMT-01` 格式渲染断言通过，生成的样本数据与题目示例完全对齐。
